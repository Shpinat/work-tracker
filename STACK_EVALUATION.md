# Work Tracker: архитектурный аудит и оценка технологического стека

## 1. Резюме
Проведён глубокий архитектурный и технический аудит репозитория. Текущий Work Tracker представляет собой ванильное PWA-приложение (HTML, CSS, JS), построенное на принципах модульности (ES Modules) и клиентского хранения данных (localStorage) без сборщиков и фреймворков.

Исходя из подтвержденных требований (единоличная разработка с ИИ-агентами, приоритет на *максимальное упрощение* вплоть до удаления аналитики, отказ от усложнения бизнес-логики и **критически важное требование полного офлайн-доступа**), **главный вывод:** внедрение React, Vite или системы сборки нецелесообразно. Они создадут неоправданные инфраструктурные риски для Service Worker'а и усложнят проект, не дав взамен необходимых преимуществ.

Наилучшим решением является сохранение текущего стека (Vanilla JS) с внедрением *ненавязчивых* инструментов контроля качества (JSDoc + TypeScript Compiler в режиме проверки) для защиты от регрессий при рефакторинге.

## 2. Фактическая архитектура
Анализ кода (`app.js`, `domain/*.js`, `ui/*.js`, `data/*.js`) показал следующую картину:
- **Стек:** Vanilla JS (ES Modules), HTML5, CSS3, Service Worker (`sw.js`). Сборщика (package.json) нет.
- **Архитектура:** Четкое разделение на слои.
  - `domain/` — чистые функции расчетов (`payroll.js`, `analytics.js`).
  - `data/` — работа с `localStorage` и файлами (`storage.js`, `backup.js`).
  - `ui/` — рендеринг и манипуляции DOM.
  - `app.js` — слой координации (оркестратор).
- **Состояние (State Management):** Управляется глобальными переменными в `app.js` (`shifts`, `settings`, `currentDate`) и синхронно сбрасывается в `localStorage`.
- **Хранение данных:** Плоский JSON-словарь в `localStorage`. Ключи — даты (O(1) доступ).
- **Офлайн и PWA:** Реализован кэширующий `sw.js`. Приложение может быть установлено и работать без сети.

**Подтверждённые сильные стороны:** Бизнес-логика (`domain/payroll.js`) уже изолирована от DOM и побочных эффектов. Применяются оптимизации обхода данных (например, лукапы дат вместо сканирования словаря).

## 3. Проблемы, требующие решения
Хотя архитектура проста и эффективна, есть обоснованные риски при дальнейшем "упрощении" кода ИИ-агентами:
1. **Риск случайных регрессий (отсутствие типов):** Так как `localStorage` хранит сериализованные объекты, легко допустить опечатку (например, `shift.totalpay` вместо `shift.totalPay`) при рефакторинге.
2. **Безопасное удаление кода:** Поскольку приоритет — удаление фич (например, аналитики), отсутствие статических анализаторов повышает риск оставить "висячий" код или удалить нужную зависимость.
3. **Хрупкость DOM-связок:** `app.js` жестко привязан к ID элементов. Удаление части интерфейса потребует аккуратной зачистки кэша элементов (`const elements = {...}`).

## 4. Сравнение вариантов A–D

| Критерий | A: Текущий стек | B: JS + Строгий контроль (JSDoc/TS Check) | C: TypeScript без React | D: React + TS + Vite |

| **Соответствие размеру приложения** | 5 | 5 | 4 | 2 (Overkill) |

| **Простота разработки (для ИИ/1 чел.)** | 4 | 5 (Типы помогают ИИ) | 4 | 3 |

| **Производительность и размер** | 5 (Без бандла) | 5 | 4 | 3 |

*Пояснения:* Вариант **B** выигрывает, так как решает проблемы надежности без затрат на миграцию и рисков для Service Worker, свойственных вариантам C и D. Вариант **D** получил низкие оценки из-за того, что проект не требует усложнения UI, а внедрение бандлера может поставить под угрозу стабильность жестко требуемого офлайн-режима.

## 5. Оценка отдельных инструментов

- **JSDoc + TypeScript Compiler (с флагом `allowJs` и `checkJs`):** *Внедрить сейчас.* Не меняет исходники, но даёт ИИ и редактору понимание структур данных.
- **Vite / Webpack / Parcel:** *Не использовать.* Приложение прекрасно работает через ES Modules. Сборщик добавит шаг компиляции, который усложнит жизнь разработчику и создаст риски кэширования PWA.
- **React / Vue / Svelte:** *Не использовать.* UI будет только упрощаться. Компонентный фреймворк здесь — решение несуществующей проблемы.
- **Vitest (или Node.js `--test`):** *Внедрить позднее.* Если бизнес-логика (расчеты часов/оплаты) начнет ломаться при рефакторинге, стоит добавить тесты для папки `domain/`. Нативный Node test runner предпочтительнее (0 зависимостей).
- **ESLint / Prettier:** *Внедрить сейчас (базово).* Защитит от грубых синтаксических ошибок при массовом удалении кода.

## 6. Стоимость миграции
Поскольку рекомендуется **Вариант B (JS + Строгий контроль)**, трудозатраты минимальны:
- **Настройка (tsconfig.json, JSDoc):** 0.5–1 день.
- **Адаптация бизнес-логики (типизация):** 1 день.
- **Миграция UI/PWA/Хранилища:** 0 дней (не требуется).
*Неопределенность:* Время на исправление потенциальных несоответствий типов, которые найдет TS Compiler в текущем коде.

Для сравнения, переход на **React (Вариант D)** занял бы 10-15 дней (переписывание всего `app.js` и `ui/`, настройка бандлера, перенос логики PWA).

## 7. Сценарии развития

### Сценарий: Архитектурное "Обезжиривание" (Рекомендуемый)
Цель: Повысить надежность существующей базы для безопасного удаления лишних функций (аналитика и т.д.).
- **Изменения:** Добавление `tsconfig.json` (проверка JS), покрытие JSDoc-аннотациями `domain/` и глобального состояния (`shifts`, `settings`). Последовательное удаление неиспользуемых UI-модулей.
- **Польза:** ИИ-агент (и разработчик) видит предупреждения, если при удалении аналитики случайно сломалась структура смен.
- **Сохраняемые части:** Вся архитектура, нативный HTML/CSS, ES Modules, `sw.js`.

## 8. Пошаговый план
1. **Базовый контроль:** Добавить `tsconfig.json` для проверки JS (без компиляции).
2. **Типизация данных:** Описать JSDoc-интерфейсы для объекта смены (`Shift`), настроек (`Settings`) и глобального состояния.
3. **Рефакторинг (Упрощение):** Начать безопасное удаление модулей аналитики из UI и `domain/`, опираясь на подсказки TS-сервера о "висячих" ссылках.
4. **Очистка DOM-биндингов:** Удалить лишние селекторы из объекта `elements` в `app.js`.

## 9. Риски и сохранность данных
Самый уязвимый компонент при любых изменениях — формат хранения в `localStorage` и Service Worker.
- При удалении фич (например, аналитики) нельзя удалять старые поля из объектов смен в `localStorage`, если есть риск, что они понадобятся для обратной совместимости экспорта.
- Обновление PWA: Любые изменения в JS/CSS/HTML *обязывают* инкрементировать `CACHE_NAME` в `sw.js`, иначе пользователи в офлайне (и даже в онлайне) не увидят обновленный, упрощенный интерфейс.

## 10. Что не следует делать
- **Не внедрять React, Redux, Tailwind.** Проект требует максимального упрощения.
- **Не переводить файлы в `.ts`.** Компиляция усложнит деплой (потребует CI/CD pipeline для сборки) и нарушит текущую ванильную гармонию.
- **Не менять структуру `localStorage`.** `Object.keys()` и лукапы по дате работают быстро.

## 11. Финальная рекомендация
- **Рекомендуемый стек:** Вариант B. Оставить **Vanilla JS (ES Modules) + HTML + CSS**, добавив поверх **JSDoc и TypeScript Compiler** только в режиме статической проверки (`checkJs: true`).
- **Что внедрить:** `tsconfig.json` (для IDE и ИИ-агента) и, опционально, встроенный в Node.js раннер тестов для `domain/payroll.js`.
- **От чего отказаться:** От любых бандлеров (Vite, Webpack), транспайлеров (TS -> JS) и UI-фреймворков (React).
- **Условия пересмотра:** Если в будущем (через несколько лет) возникнет требование добавить сложную облачную синхронизацию с разрешением конфликтов (CRDT) и веб-сокетами, текущая монолитная архитектура `app.js` перестанет справляться, и потребуется внедрение реактивного менеджера состояний. До тех пор текущий стек идеален.
